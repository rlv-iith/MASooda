# MASooda Comprehensive Technical Audit

**Audit date:** 2026-11-06  
**P2 owner:** Lalith (ADMM conflict resolution). This report is a project audit and proposed work plan; it does not claim the listed fixes have already been implemented.  
**Scope:** repository source, configs, README, proposal, available technical notes, tests inventory, experiment scripts, and saved output artifacts.  
**Status:** static audit; no source changes, simulation reruns, or tests were performed.

## 1. Executive assessment

MASooda is a useful integrated research prototype, not a validated aircraft traffic-management system. Its main loop joins local Boids-style control, a corridor overseer, grouped ADMM, an attack/report pipeline, and STL monitoring. The code is modular and the test suite covers many individual functions. The repository also has reproducible experiment scripts and a substantial set of saved figures and CSVs.

The most important issues are in the meaning of the results, not simply runtime bugs:

1. Safety is measured in horizontal distance even though the implementation treats altitude layers as non-colliding. The safety specification says Cartesian distance and accepts 2D or 3D, so the layer policy, physical height, solver constraints, and reported robustness do not share one collision definition.
2. The security story overstates the integrated W-MSR defense. The engine's defense path range-corrects reports using true-neighbor state; its W-MSR estimate is calculated but not used by local behavior. ADMM receives truth-state intents. The attack code only implements common broadcast, not the configured per-neighbor mode.
3. ADMM is a local heuristic, not a safety guarantee. Conflict groups are capped by chunking, candidates are restricted to the merge zone by default, and the engine ignores non-converged solutions. The saved P3 merge result reports minimum distances of 0.411 m with ADMM and 1.307 m without it, both far below the configured 8 m threshold.
4. The saved experiment record is not yet a defensible statistical evaluation. Several results are single-seed; current output CSVs include a scaling row with zero solver calls, and the scaling note describes expected trends rather than a completed results table.
5. The nominal world is a corridor abstraction. Obstacles, intersections, actual communication latency/loss for agent links, aircraft dynamics, and real physical altitude are not represented in the main model. That is acceptable for a scoped prototype if stated clearly, but the proposal/demo language should not imply those capabilities are already demonstrated.

**Recommendation:** first make safety semantics and security experiments truthful and measurable; then repair conflict-group handling and numerical diagnostics; only afterward invest in large sweeps. At 60 agents and 0.1-second steps, a single ordinary run is small. HPC's scientific value is in paired multi-seed, sensitivity, and scale studies, not GPU acceleration of the current run.

## 2. Project objective and current model

The proposal's intended system has local drone-to-drone decisions, a higher-level DTC/overseer, heterogeneous priorities, conflict resolution, resilient behavior under communication loss and false information, minimum-separation monitoring, and arrival at destinations. The approved scope excludes detailed aircraft physics and certification, but expects bounded 2.5D corridors, intersections, entry/exit zones, obstacles, and communication capabilities.

The implemented main simulation in `simulation/engine.py` uses a fixed fleet and fixed timestep. `simulation/dynamics.py` applies horizontal double-integrator kinematics with acceleration and speed clamping; altitude is a discrete integer layer. `local_behavior/boids.py` generates velocity commands. `simulation/overseer.py` periodically makes corridor and altitude assignments. `conflict_resolution/` detects nearby conflicts and applies one-tick ADMM. `resilience/` injects position reports and computes a report correction/W-MSR estimate. `verification/` computes separation robustness and run metrics.

The ADMM problem is a weighted projection toward target positions under speed-ball and pairwise half-space constraints. The pairwise safe-distance constraint is non-convex in its exact Euclidean form and is linearized along the current pair separation direction. This is a reasonable local approximation, but only for the pairs represented in that solve. The code runs the calculation independently for groups returned by conflict detection.

The configured baseline is 60 agents, `dt=0.1 s`, `duration=180 s`, desired speed 12 m/s, speed cap 15 m/s, acceleration cap 4 m/s², horizontal minimum distance 8 m, 3 corridors, 20 m corridor width, 50 m centerline spacing, 15-agent nominal corridor capacity, 3 nominal layers, and 30 m layer height. The main `main.py` MVP deliberately enables an attack and an overseer outage for 90–120 seconds even though `attack.enabled` and link failure are false in the base YAML; `--scenario nominal` disables those effects.

## 4. Before-and-after simulation picture

### Current simulation

- **State:** horizontal x/y, velocity and acceleration; z is effectively a layer integer. No rotation, climb dynamics, vehicle dimensions, winds, or actuation delay.
- **Initial conditions:** synthetic 60-agent population from a seed; all start in entry zones and are horizontally separated by rejection sampling. Fleet types are sampled from configured proportions; corridor assignment initially cycles over three corridors.
- **Boundary/route model:** straight parallel corridors, prescribed merge zone and exit x range. There is no explicit obstacle or intersection geometry, no queue at corridor capacity, and agents are not removed at destination.
- **Control:** local desired velocity followed by first-order velocity tracking `a=(v_des-v)/tau_v`, acceleration/speed clamping, and explicit position update from the old velocity. With dt=0.1 s, the nominal run has 1,800 integration steps.
- **Conflict solve:** detected current-distance graph, optional merge-zone restriction, components chunked to at most five, one-step 2D ADMM with a 50-iteration limit. Converged velocities replace local desired velocities; nonconverged solutions are ignored by the engine.
- **Safety output:** minimum horizontal separation minus 8 m. Violation ticks count samples below zero; this is not a continuous-time guarantee between samples.
- **Control/security:** the main MVP enables one position falsifier after 60 s and an overseer outage from 90 to 120 s. V2V state is otherwise instantaneous and complete within geometric range.

### Corrected target simulation

First, hold the basic kinematic model and fixed fleet so the impact of semantic and algorithmic corrections can be isolated. Make layer height/clearance and STL distance consistent; define actual arrival and capacity behavior; preserve every detected conflict edge; have the defense consume only permitted information; and label/record solver convergence and fallback. Then add temporal prediction and agent-link uncertainty as separate experiments. A better model is not expected to produce prettier trajectories: corrected safety metrics may show more violations because the old evaluator did not measure the declared physical quantity or because less optimistic information is available.

Use at least these scenario classes: normal lane following; merge contention; crossing trajectories; emergency priority contention; overseer outage; V2V outage/latency (if in scope); common spoof; per-neighbor spoof (after implementation); and high-density/capacity overflow. For each, run paired seeds across baseline and intervention. Report valid arrivals, safety robustness, violation episodes and recovery time, minimum predicted separation, ADMM convergence/fallback, directive age, queue/overflow, and compute cost.

### Likely changed / stable findings

- **Likely changed materially:** cross-layer safety violation counts and min separation (D01/D12); ADMM event count and trajectories (D05/D06); defended attack results (D02/D03); arrivals/throughput (D09/D10/D11); run-to-run uncertainty (D16/D17).
- **Should remain comparable if setup is preserved:** basic uncongested straight-line kinematics, config defaults, schema serialization, and isolated consensus toy results.
- **Conclusions to withdraw pending re-evaluation:** “ADMM ensures minimum separation”; “integrated W-MSR mitigates flight-control attacks”; “all counted agents reach their destination”; “corridor capacity is respected for 60 agents”; “per-neighbor Byzantine attack has been demonstrated”; and “full real-time dual-screen system is already implemented.”

## 5. HPC strategy

### Appropriate now

| Workload | Question and implementation | Compute | Scientific value / cost decision |
|---|---|---|---|
| Paired multi-seed evaluation | Do interventions improve safety/throughput reliably over random initial populations? Run baseline and each fix for the same seed/scenario; aggregate distributions and paired differences. Use `ProcessPoolExecutor` or a Slurm job array; one process per independent run. | CPU, embarrassingly parallel; start 30–100 seeds per scenario after a pilot. | **High value, justified.** Likely the best HPC use. Store a compact metrics row and manifest per run; avoid retaining all trajectories unless selected for plots. |
| Parameter sensitivity / calibration | Which settings govern violation rate, throughput, and convergence? Use Latin hypercube or Sobol sampling for continuous weights, detection radii, timeout, and capacity; categorical policy sweep separately. Use SALib or SciPy + custom runner. | CPU process/job array. Begin with a low-cost 10–20 point pilot, expand based on variance. | **High value, justified after correctness.** Avoid tuning solely to a single seed or optimizing only safety at the expense of liveness. Freeze a holdout seed set. |
| Fleet scaling | At what density or N do grouping and communication become bottlenecks? Scale N (e.g. 60, 120, 250, 500) and duration with fixed density, plus fixed area/density alternatives. Profile detector, solver, monitor and rendering separately. | CPU; potentially multi-node only for many independent jobs. | **Medium/high value.** Establishes scalability claims; no MPI inside a single 60-agent run is warranted. |
| Uncertainty / Monte Carlo | How sensitive are outcomes to jittered initial position, type mix, communication loss, and attack timing/offset? Use explicit distributions and independent streams. | CPU; job arrays. | **High value** for confidence intervals and robust conclusions. Use physically/scenario-justified distributions; do not add arbitrary stochasticity. |
| High-resolution event re-simulation | Are close passes missed by 0.1 s sampling? Replay selected encounters at 0.02 s or use swept-disc/continuous closest-approach calculations over each step. | CPU, per-run; can parallelize encounter cases. | **High value and affordable.** Better than globally reducing dt before establishing which events need refinement. |

### Not justified yet

- **GPU/CUDA:** current core workload has tens of agents and small 2D projections; Python orchestration, grouping, and I/O dominate likely. GPU transfer/launch overhead is unlikely to help. Reconsider only if measured large-N vectorized kernels or learned policies dominate.
- **MPI/distributed-memory single simulation:** no spatially distributed state or coupled high-dimensional PDE exists. Use Slurm job arrays/process pools for independent runs instead.
- **Multiphysics CFD/airflow:** no project question currently depends on wake or wind fields. Add only if wind sensitivity or wake interaction becomes a stated research question with validated data.
- **Mesh refinement:** there is no mesh/grid-based PDE. Replace this concept with time-step refinement and geometric/safety-model refinement.

For an illustrative memory scale, one float64 `(T=1801,N=60,D=3)` position array is about 2.5 MB; positions and velocities together about 5 MB. This is small for HPC. Do not make claims about speedup until the same workload is benchmarked serially and in parallel with fixed software/hardware metadata.

## 6. Final demonstration architecture

1. **Problem and scope (1 slide):** show the proposal objective and one clear schematic of corridors, agent types, overseer, V2V links, and measured safety. State “kinematic corridor simulation” and excluded real-aircraft physics.
2. **What exists today (1 slide):** architecture diagram and a short baseline run. Identify implemented vs planned features; show current observed violations rather than hiding them.
3. **Model and assumptions (2 slides):** show the state vector, dynamics equations, Boids terms, ADMM objective/constraints, layer-clearance rule, arrival region, and attack assumptions with units. Mark convexification and sampled-time limitations.
4. **Audit corrections (1 slide):** concise before/after table: safety semantics; trusted data path; constraint coverage; arrival/capacity; reproducible experiment manifest.
5. **Method and computational design (1 slide):** dt, duration, seed pairing, scenarios, metrics, stopping/fallback criteria, plus why CPU job arrays were selected and GPU/MPI were not.
6. **Live or recorded scenario (2–3 min):** normal flow, merge, emergency priority, then an explicitly labeled fault scenario (attacker and/or DTC outage). Overlay layer, corridor assignment, attacker, predicted closest approach, and fallback state. If only offline GIF/PNG exists, call it a recorded run, not a live dashboard.
7. **Safety evidence (2 slides):** robustness vs time with zero threshold, pair identity, violation episodes; paired-seed distributions with uncertainty; corrected 3D/layer-aware definition. Avoid a single trace as proof.
8. **Resilience evidence (1–2 slides):** compare no attack, attack without defense, range-only baseline, and actual filtered defense; show graph assumptions and report error. Clearly label empirical result and conditions; no formal guarantee unless proved.
9. **Performance and scale (1 slide):** convergence/fallback distributions, solver and detection wall time, N scaling, throughput and queueing. Separate algorithm time from plotting and persistence.
10. **Conclusions / limitations (1 slide):** state what is demonstrated, what failed, what remains unsupported, and the next experiment. A scientifically credible result can show that some methods did not meet the 8 m target.

Recommended visuals: top-down trajectories with corridor boundaries; optional side view with physical altitude; robustness time series; violin/box plots across seeds; throughput-vs-safety Pareto chart; ADMM residual/convergence plot; occupancy/capacity and queue plot; attack estimate error plot; runtime-vs-N plot. Each plot should show units, seed count, scenario, threshold, and confidence interval where applicable.

## 10. Demonstration-ready checklist

- [ ] One collision definition in meters is used by ADMM, live STL, offline metrics, charts, and documentation.
- [ ] Layer identifiers and physical altitude are not conflated.
- [ ] Solver reports all detected constraint edges, convergence, residuals, feasibility, and fallback.
- [ ] No result or UI label describes ADMM as a guarantee unless a separate proof/safety filter supports that claim.
- [ ] Attack data flow is explicit; W-MSR values actually reach the intended controller; no hidden ground-truth input is used except in a labeled oracle baseline.
- [ ] Unsupported attack modes fail validation; supported common and per-neighbor modes replay deterministically.
- [ ] Arrival, throughput, capacity, queueing, and terminal behavior have unambiguous definitions.
- [ ] Paired seeds and confidence intervals support claims; missing solver rows are not interpreted as zero cost.
- [ ] Every output has resolved config, seed, code revision, software/hardware details, and a run manifest.
- [ ] Full unit/integration suite and analytic safety cases pass in the final environment.
- [ ] Documentation distinguishes implemented, experimental, deferred, and out-of-scope features.
- [ ] Final animation/dashboard is labeled live or recorded accurately and agrees with machine-readable CSV/JSON metrics.
- [ ] Limitations and negative/failed results are shown alongside successful cases.

## 11. Audit limitations

The audit inventoried the repository files and inspected the main architecture, all core implementation packages, experiment scripts/tests inventory, README/configuration, technical Markdown notes, the proposal PDF, Boids formulation PDF, threat-model PDF, and saved output CSV headers plus selected result rows. The test suite and simulations were not executed, and not every historical CSV row or image pixel was independently reprocessed. The Git working tree was read successfully with an explicit per-command safe-directory override; the pre-existing untracked output artifacts and `web_sandbox/` were left untouched. Findings above distinguish code-confirmed behavior from missing validation and proposed research extensions.
